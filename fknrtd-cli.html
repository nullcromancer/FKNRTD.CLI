Nullcromancer // Instrument 001

FKNRTD.CLI

A terminal command center for coding agents that are not trusted on their word.

Several machines write code for you. None of them can be believed. This is the desk they all report to: it isolates their work, runs the checks itself, makes a second machine review the first, keeps the paperwork, and refuses to merge anything until you personally say the word.

Premise // Why this exists

The report is not the work

An agent that says "done, all tests pass" has told you nothing. It has produced a sentence. FKNRTD.CLI is built on the assumption that the sentence is worthless and only evidence counts.

So the tool never asks an agent whether the work is good. It runs the verification commands itself, in a worktree it created, and then hands the diff to a different agent for review. Implementation and audit are never the same seat. When both pass, the task stops and waits for a human.

01

Isolation

Every task gets its own Git branch and worktree. Two agents working at once cannot overwrite each other, because they are not in the same directory.

02

Deterministic proof

Your verification commands are executed by the orchestrator, not by the agent that wrote the code. Exit codes are recorded. Output tails are kept.

03

Adversarial review

A second agent reads the real diff and must end with an exact verdict marker. An ambiguous verdict is treated as failure, never as a pass.

04

Human landing

Nothing merges on its own. A finished task sits in ReadyToLand until you type a confirmation token.

Design rule

The command center is never the source of truth. Git holds the code, the agent CLIs hold their own state, your test suite holds the verdict. This tool collects, correlates and displays. When it disagrees with Git, Git is right.

Pipeline // Eight stages, one loop

Brief to Land, with a bounded repair cycle

StageOwnerWhat actually happens
BrieforchestratorWrites brief.md with the request and the acceptance commands.
WorktreeorchestratorCreates branch fknrtd/<task>-<title> and an isolated worktree.
PlanLeadRead-only pass. Produces plan.md. Forbidden from editing.
ImplementImplementerWrites code inside the worktree only. Changed paths are recorded.
VerifyorchestratorRuns your commands through the system shell. Exit codes and output tails stored.
AuditAuditorReads the real diff. Must emit exactly one verdict marker.
ReadyToLandorchestratorCommits verified changes. Stops. Waits for a human.
LandyouMerges --no-ff after every gate passes.
The verdict contract

The auditor must finish with FKNRTD_VERDICT: PASS or FKNRTD_VERDICT: FAIL alone on a line. The prompt contains both markers, so the orchestrator strips its own prompt from the reply before counting. One PASS and zero FAIL is a pass. Anything else — both markers, neither marker, two passes — fails. Ambiguity never merges.

Seats // Who does what to whom

Three roles, deliberately not collapsed

Lead

Plans in read-only mode. Inspects the repository, names the files that will change, states the risks. Produces no code.

Implementer

Writes the change inside the isolated worktree. Cannot merge. Cannot leave the worktree. Its report is treated as a claim, not evidence.

Auditor

Reads the diff and the verification results. Read-only. Must return an explicit verdict. Should not be the same agent that implemented.

Any command-line coding tool can hold any seat. Claude Code and OpenAI Codex CLI ship configured; anything else is a JSON object away.

Registering another agent

agent registration
# arguments are an array, so there are no quoting rules to get wrong
fknrtd agent add -id gemini -exe gemini -arg=-p -arg="{prompt}"

# or supply a full definition with per-stage profiles
fknrtd agent add -file examples/generic-agent.json

Placeholders substituted at launch: {prompt}, {taskId}, {workspace}, {branch}. A profile may deliver the prompt as an argument or on standard input.

Sandboxing is theirs, not ours

Worktree isolation prevents agents colliding with each other. It is not a security boundary. Only the agent's own CLI can constrain what it touches — use its read-only or plan mode for the Plan and Audit seats.

Install // One tool, no supply chain

Requires .NET 10 SDK and Git 2.28 or newer

windows
scripts\install.cmd
posix
./scripts/install.sh

Both pack src/FKNRTD.Cli into artifacts/ and install or update the global tool. Restart the terminal if fknrtd is not immediately on PATH. Confirm with:

verification
fknrtd --version        # FKNRTD.CLI 1.0.0
fknrtd doctor           # .NET, Git, config, writable state, every agent

doctor reports rather than throwing. An agent that is not installed shows as a failed check, not a crash.

Zero dependencies, deliberately

No PackageReference exists in any project. The entire product is the .NET base class library. Nothing is vendored, nothing is transitive, nothing else can be compromised on your behalf.

Quickstart // First supervised task

From empty repository to merged, verified work

01 // initialise
cd /path/to/your/repo
fknrtd init
git add .fknrtd/config.json .fknrtd/.gitignore
git commit -m "Configure FKNRTD.CLI"
fknrtd doctor

init requires an existing Git repository and detects your verification commands where it can. Commit the config: it is reviewable project policy, and an uncommitted state directory will block landing later.

02 // commission the work
fknrtd task create "Add JWT validation" \
  -brief "Validate the signature and expiry on every inbound request.
          Reject with 401. Do not change the login path." \
  -verify "dotnet test" \
  -lead claude -implementer codex -auditor claude
03 // run and watch
fknrtd task run FKN-20260915-163416-cf12aec4
fknrtd task show FKN-20260915-163416-cf12aec4   # per-stage results
fknrtd dashboard                                # live command center
04 // land it yourself
fknrtd task land FKN-20260915-163416-cf12aec4 -confirm LAND
fknrtd task cleanup FKN-20260915-163416-cf12aec4 -confirm REMOVE
What landing checks before it will move

The primary worktree is clean. You are on the task's base branch. Verification passed. The audit returned a single PASS. You typed -confirm LAND. Any one missing and the merge is refused with the reason.

Treat this file as code

Verification commands are executed through cmd.exe on Windows or /bin/sh elsewhere. A malicious or careless edit to config.json is arbitrary code execution on your machine. Review changes to it exactly as you would review a build script. Commit it so the change is visible.

No environment variables configure behaviour. The process reads PATH, PATHEXT and COMSPEC only, to find executables and pick a shell. It stores no credentials: every agent authenticates itself.

Effective Use // Operator doctrine

The difference between a useful run and an expensive one

1. A brief is a contract, not a wish

The single largest quality lever. Name the files. State what must not change. Give the acceptance criteria as commands, not adjectives. "Improve error handling" produces an expensive mess; "Wrap every call in PaymentClient so a timeout returns Result.Failure, do not change the retry policy, dotnet test must pass" produces a diff you can review in a minute.

2. Never let one agent implement and audit

A model reviewing its own work agrees with itself. Put a different vendor in the Auditor seat if you can, a different model at minimum. This is the entire point of the tool; collapsing the seats turns it into an expensive script runner.

3. Give it a real verification command

With no commands the Verify stage is skipped and the audit becomes the only gate — you are back to trusting prose. A build alone is weak evidence. A build plus tests that would actually fail is the thing that makes the repair loop work.

Watch for empty evidence

A verification command that passes without doing anything is worse than none, because it looks like proof. dotnet test against a project with no tests exits zero. Check that your gate can fail before you trust it.

4. Keep the repair budget low

The default is one round, and that is usually right. An agent that could not satisfy a clear brief and a failing test in two attempts is not going to find it on the fifth; it is going to write increasingly speculative code while spending your allowance. A failed task with evidence beats a passed task with damage.

5. Mind the agent lease

An agent runs one task at a time, enforced by an exclusive lease. If Claude holds both Lead and Auditor and you start several tasks at once, they serialise; a long first task can make a later one fail on lease timeout. Spread the seats across agents before you raise maxParallelAgents.

6. Read the evidence, not the summary

When something looks wrong, go to the artifacts. The plan says what the Lead intended, the audit says what the Auditor actually found, the logs say what the process actually printed. Every one of them is a file on disk with no interpretation layer.

7. Land deliberately

The confirmation token is not ceremony. It is the last point at which a human reads a diff that three machines have agreed about. Read it.

Task shapes that work well — and badly

Well: bounded refactors, adding a method to an existing class, migrating a call site pattern, adding tests to an untested unit, mechanical renames, fixing a reproducible bug with a failing test attached.

Badly: open-ended design, anything needing product judgement, work whose acceptance cannot be expressed as a command, changes spanning many modules at once, and anything where you cannot describe "done" in a sentence.

Writes are atomic: temporary file, then rename. History is JSON Lines, read from the tail and rotated past a size cap, so a long-lived project does not make the dashboard slower every day. A per-task exclusive lease stops two processes running the same task.

Machine-readable state for your own tooling:

snapshot
fknrtd status -json | jq '.tasks[] | {id, status, stage}'
fknrtd status # exit 3 == live collision, usable in a pre-commit hook

Symptom, cause, remedy

SymptomWhat it means

Agent shows OfflineIts executable did not resolve on PATH. Run doctor.
Task is busy / lease heldAnother process owns it. The message names the holding process id.

Commit refused, no identityuser.name and user.email are unset in that repository.

fknrtd not found after installRestart the terminal so PATH is refreshed.

Cancellation is a file marker: fknrtd task cancel <id> requests it and running stages observe it within half a second. A cancelled task can be resumed with task retry.

Limits // Stated plainly

What this tool does not do, and will not pretend to

  • It is not a sandbox. Worktrees stop agents colliding. They do not stop an agent reaching the rest of your filesystem. Only the agent's own CLI can do that.
  • It cannot make a bad brief good. Vague instructions produce vague diffs, faster and at greater expense than doing it yourself.
  • An audit is a second opinion, not a proof. A model can approve wrong code convincingly. The deterministic commands are the hard evidence; the audit is judgement on top of it.
  • Verification is only as good as your commands. The tool records exit codes faithfully. It cannot tell that your test suite asserts nothing.
  • Display width is terminal-dependent. Layout follows East Asian wide and fullwidth plus emoji presentation. A terminal with different ambiguous-width rules will disagree.
  • POSIX paths are unverified. Development and validation ran on Windows. The /bin/sh execution path and install.sh have not been exercised on Linux or macOS.
  • No telemetry leaves your machine. There is no server, no endpoint, no metrics exporter. Capacity figures come from the agent CLIs you already run.
Evidence standard

Every figure quoted in this document was produced by running the command on a real machine against a real commit. Where something was not measured, it is not claimed. See VALIDATION.md for the record and its stated limits.
